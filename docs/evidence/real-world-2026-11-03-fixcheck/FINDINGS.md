## First fix attempt and separate adaptive repeat

The first committed fix attempt is retained in [sets/news](sets/news/). It exposed two additional implementation gaps: the actual post CLI did not supply a release client to relative-period resolution, allowing an older companyfacts quarter to win over an eligible new release (RW033); and a model could stop after empty XBRL lookups without trying the available 6-K (RW050). These are routing defects, not grounds to lower the source requirements.

The [separately registered adaptive code repair](sets/news-r2/protocol.json) repeats all 80 items, retains the complete first attempt, freezes its own code and inputs before execution, and charges the same root ledger. Its results remain post-hoc and are displayed alongside the first attempt. No individual provider/path result is chosen as a replacement or a best-of score.

For RW033, all three first-attempt post paths selected FY2026Q3, filed 2026-07-29, and contradicted the claim. All three adaptive post paths instead record **“period resolved from post date 2026-10-29 → FY2026Q4, filed 2026-10-29”** and support it: [Baseten](sets/news-r2/baseten/post/RW033/report.json), [Fireworks](sets/news-r2/fireworks/post/RW033/report.json), [Meta](sets/news-r2/meta/post/RW033/report.json). This demonstrates the repaired default release-discovery route. RW033 retains its original `review_required` gold and is excluded from the four-case truth score; publication-date inference is not independent gold review or proof of intraday availability.

Provider failures remain distinct from source abstentions. For example, the adaptive [Fireworks RW006 post check](sets/news-r2/fireworks/post/RW006/result.json) retains an `APITimeoutError` after extraction. It counts wrong in the primary panel and remains a failed item, rather than being relabeled as insufficient evidence or replaced with its successful first-attempt result.
